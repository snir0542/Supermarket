# supermarket-prices

מחירי סופרמרקטים בישראל מתוך קבצי השקיפות של הרשתות (חוק שקיפות מחירים), כפרויקט TypeScript עצמאי לחלוטין.
אין תלות בקוד של פרויקט אחר: ה-downloader, ה-parser, הנרמול, ה-API וה-MCP נכתבו כאן מאפס.

**הערך המוסף הוא שכבת הנרמול**, לא ההורדה: חיבור מוצרים בין רשתות לפי ברקוד (GTIN), התאמת שמות בעברית עם fuzzy matching,
היסטוריית מחירים ב-Postgres ובדיקות איכות/טריות לכל רשת. מעל זה: API ושרת MCP לסוכנים. כולל ממשק web בעברית.

> רשימת הרשתות והלינקים הרשמיים: https://www.gov.il/he/departments/legalInfo/cpfta_prices_regulations

## אונליין בלבד ו-Node 26

ברירת המחדל היא `ONLINE_ONLY=true`: קליטה, API ו-MCP מוגבלים לרמי לוי, קרפור, שופרסל וויקטורי ולחנויות שסומנו `StoreType=2` בקובץ Stores. הממשק מציג אונליין בלבד גם אם נשמרה בדפדפן בחירה ישנה בסניפים פיזיים. נתונים פיזיים שכבר קיימים במסד אינם נמחקים, אבל אינם משתתפים בחיפוש, בטווח המחירים, בהיסטוריה, בסל או בדוח הטריות. אחרי השדרוג הריצו `npm ci` והפעילו מחדש את ה-API ואת הממשק. ה-API ימשוך את הנתונים בעצמו.

- רמי לוי: 039; קרפור: כל חנויות האונליין שמפורסמות, לא רק 471; שופרסל: 413. הזיהוי מגיע מקובץ Stores, לא מהנחה לפי שם.
- שופרסל: בקשות מחירים מסוננות לפי החנויות שזוהו, ולא מורידות דפי סניפים פיזיים. הפרשי SubChainID וקודי סניף מרופדים מנורמלים לפי Stores כאשר ההתאמה חד-משמעית.
- ויקטורי: חנות אונליין 097 (תת-רשת 001), מזוהה בקובץ Stores כ-אינטרנט. מסלול ברירת המחדל מוריד קבצי XML/gzip מקוריים מארכיון צד-שלישי over.org.il, לא טבלאות מחירים מעובדות. אומת חי ב-2026-10-08: 8,709 מחירים ב-SQLite על Node 26, ללא שורות לא תקינות. כשל לא מוחלף בסניף פיזי או בנתוני דמו.
- קבצי השקיפות הם מחירי מוצרים, לא מחיר checkout: דמי משלוח, זמינות לפי כתובת ומבצעים מותנים אינם נכללים בסל.
- `ONLINE_ONLY=false` מחזיר את מצב הקליטה/שרת הישן לכל הרשתות והסניפים. ממשק ה-web נשאר אונליין בלבד.

התאמה ל-Node 26: `better-sqlite3` עודכן ל-13, Docker משתמש ב-Node 26, ובדיקות ה-web רצות עם `--no-experimental-webstorage` כדי למנוע התנגשות עם `localStorage` של Node. נבדקו התקנה/טעינת SQLite, בדיקות, build וקליטה חיה ב-Node 26.11.1. במעבר מגרסת Node אחרת יש להריץ `npm ci` מחדש כדי להתקין את המודול הבינארי המתאים. ללא binary מוכן יידרשו כלי build מקומיים (C++/Python).

## מה יש בפנים

| תיקייה | תפקיד |
|---|---|
| `src/downloader` | הורדה ישירה של קבצי המחירים: שופרסל (טבלת HTML + קישורי blob חתומים), קרפור (תיקיית תאריך + JSON), ויקטורי (ארכיון קבצי מקור over.org.il; API של Laibcatalog שמור כאפשרות) ופורטל `url.publishedprices.co.il` המשותף להרבה רשתות |
| `src/parser` | פענוח gzip + קידודים (UTF-8 עם BOM, UTF-16, windows-1255) ו-XML של מחירים/סניפים עם וריאציות תגיות |
| `src/normalize` | `gtin.ts` (ולידציה ונרמול ל-13 ספרות), `hebrew.ts` (ניקוד, גרשיים, אותיות סופיות, יחידות מידה, גודל), `trigram.ts`, `matcher.ts` |
| `src/db` | `schema.sql` (מוצרים, פריטי רשת, מחירים נוכחיים, היסטוריה, ריצות קליטה) ו-`PgRepository` |
| `src/ingest` | קליטה: התאמה, כתיבת מחירים, היסטוריה רק כששינוי מחיר, בדיקות איכות. `MemoryRepository` לבדיקות |
| `src/quality` | בדיקות איכות לכל קובץ ובדיקת טריות לכל רשת |
| `src/api` | API ב-**Hono** |
| `src/mcp` | שרת MCP עם ה-SDK הרשמי (`@modelcontextprotocol/sdk`): stdio ו-Streamable HTTP |
| `src/scheduler` | קליטה יומית אוטומטית: כל הרשתות, retry/backoff, בדיקת טריות |

**למה Hono ולא Fastify:** קטן, מבוסס Request/Response סטנדרטי (אפשר לבדוק עם `app.request()` בלי להרים שרת), וטיפוסים טובים. אין כאן צורך ב-ecosystem של plugins.

## איך הנרמול עובד

1. **ברקוד קודם.** `ItemType=1` וקוד שעובר בדיקת ספרת ביקורת (GTIN-8/12/13, גם GTIN-14 עם אפס מוביל) נהפך ל-13 ספרות עם אפסים משמאל, וזה המפתח בין רשתות.
   ברקודים שמתחילים ב-2 (משקל/מחיר מוטמע) וקודים פנימיים של רשת לא נחשבים ברקוד.
2. **אין ברקוד** (ירקות, מאפייה, קוד פנימי): דמיון טריגרמות על שם מנורמל. שם מנורמל = בלי ניקוד/גרשיים, אותיות סופיות מאוחדות,
   יחידות מאוחדות (`גר'`/`גרם`, `ל'`/`ליטר`, `קילו`/`קג`), מספר מופרד מיחידה. יש גם שמירת גודל: `200 גרם` לא יתחבר ל-`250 גרם`.
   - דמיון ≥ `FUZZY_AUTO_THRESHOLD` (0.8): חיבור אוטומטי.
   - בין `FUZZY_REVIEW_THRESHOLD` (0.55) ל-0.8: נוצר מוצר חדש ומסומן ב-`needs_review` (נראה ב-`GET /quality/review`).
   - מתחת: מוצר חדש.
3. **היסטוריה:** `price_history` מקבלת שורה רק כשהמחיר חדש או השתנה. `current_prices` שומר את המצב האחרון לכל סניף ומוצר.

## בדיקות איכות

לכל קובץ: קובץ ריק, `ChainId` שלא תואם לרשת (הקובץ נדחה ולא נכתב כלום), אחוז שורות לא תקינות, אחוז ברקודים תקינים נמוך,
קודים כפולים, ירידה חדה במספר מוצרים מול הריצה הקודמת, קובץ ישן. לכל רשת: `fresh` / `stale` / `never` (`GET /quality/freshness`, `npm run quality`).

## הרצה מקומית מהירה (בלי Docker ובלי Postgres)

ברירת המחדל כשאין `DATABASE_URL`: כל הנתונים נשמרים בקובץ SQLite אחד (`data/prices.db`), בלי שרת מסד נתונים.
דרישות: Node 22+ (נבדק ב-Node 26.11.1) בלבד.

```bash
git clone https://github.com/snir0542/Supermarket && cd Supermarket/supermarket-prices
npm install
npm run api                                         # משיכה אוטומטית ברקע; http://localhost:3000
npm --prefix web install && npm run web             # הממשק: http://localhost:5173
```

רוצים לראות את הממשק בלי נתונים בכלל? `npm run web:mock` (או `?mock=1` בכתובת) מריץ נתוני דמו בתוך הדפדפן.

אותו דבר עובד גם לשאר הפקודות: `npm run ingest` (ארבע רשתות האונליין), `npm run quality`, `npm run mcp`, `npm run scheduler`, `npm run ingest:all`.
הקובץ נוצר אוטומטית (`SQLITE_PATH` משנה את המיקום). מחיקת הקובץ מאפסת הכל.

**מתי לעבור ל-Postgres:** כשיש כמה תהליכים/מכונות שכותבים ביחד, כשרוצים גיבויים ושחזור מסודרים,
או כשמחזיקים את כל הרשתות והסניפים לאורך זמן (ההיסטוריה גדלה מהר). הדרך: `DB_DRIVER=pg` ו-`DATABASE_URL=...`
(`docker compose up` כבר מוגדר כך). הנתונים לא עוברים אוטומטית בין המנועים: מריצים קליטה מחדש מול Postgres.

### קליטה אוטומטית עם ה-API

`npm run api` יוצר את הסכמה (SQLite או Postgres), פותח מיד את HTTP ומתחיל משיכה ברקע של ארבע רשתות האונליין. אין צורך ב-`npm run ingest:all` לפניו. בכל הפעלה יש בדיקת קבצים עדכניים; קבצים שכבר נקלטו מדולגים. הנתונים מתווספים בהדרגה, לכן בתחילת הרצה על מסד ריק החיפוש יכול להיות ריק. `/health` מציין שהתהליך חי, **לא** שכל הנתונים מוכנים.

```bash
curl http://localhost:3000/ingest/status
curl http://localhost:3000/quality/freshness
```

`/ingest/status` מחזיר `idle`, `running`, `ok`, `partial`, `failed` או `disabled`, עם סיבת הריצה, זמנים, תוצאות לכל רשת ושגיאה אם קיימת. `ok` פירושו הצלחת הריצה, לא הבטחה שכל מחיר טרי; דוח הטריות הוא המקור לטריות. כשל ברשת אחת אינו מפיל את ה-API או מוחק נתונים קיימים. אחרי כשל, הריצה המתוכננת הבאה מנסה שוב; אפשר גם להפעיל מחדש. אין endpoint שמפעיל קליטה דרך HTTP.

ברירת המחדל כוללת גם רענון יומי ב-06:00 לפי `Asia/Jerusalem`. אותן הגדרות `INGEST_CRON`, `INGEST_HOUR`, `INGEST_MINUTE`, `INGEST_TZ`, `INGEST_RETRY_ATTEMPTS` ו-`INGEST_RETRY_BASE_SECONDS` של ה-scheduler חלות גם כאן. `INGEST_RUN_ON_START` נשאר הגדרה של ה-scheduler בלבד, ואינו משנה את ה-API.

| משתנה | ברירת מחדל | תפקיד |
|---|---|---|
| `API_INGEST_ON_START` | `true` | משיכה בכל הפעלת API; `false` מכבה |
| `API_INGEST_SCHEDULED` | `true` | רענון לפי cron; `false` מכבה |

המשתנים צריכים להיות בסביבת התהליך. `npm run api` אינו טוען `.env` בעצמו. כדי להשתמש בקובץ:

```bash
node --env-file=.env --import tsx src/api/server.ts
# או משתנים מפורשים להרצה בלי קליטה:
API_INGEST_ON_START=false API_INGEST_SCHEDULED=false npm run api
```

כדי למנוע משיכה בכלל, הגדירו את **שניהם** ל-`false`. אם scheduler נפרד/כמה עותקי API עובדים על אותו מסד, השאירו כותב אחד בלבד: כבו את שתי ההגדרות בעותקי API האחרים. ב-docker-compose המצורף ה-scheduler הוא הכותב היחיד: שתי הגדרות ה-API כבויות, ו-`INGEST_RUN_ON_START` הוא `true` כברירת מחדל של compose כדי שהרצה ראשונה תמשוך מיד. הפקודה העצמאית `npm run scheduler` נשארת עם ברירת המחדל הישנה `false`.

הקליטה משתמשת באותו repository של ה-API, כך שחיפוש fuzzy ב-SQLite רואה מיד מוצרים חדשים ללא restart. SIGINT/SIGTERM מפסיקים את התזמון וממתינים לקליטה הפעילה לפני סגירת המסד. במקרה של רשת איטית ההמתנה יכולה לקחת כמה דקות (timeouts/retries); עצירה כפויה יכולה להשאיר קליטה חלקית שדורשת הרצה מחדש. הקובץ נשמר בין הפעלות. `npm run ingest:all` נשאר זמין להרצה ידנית כשהקליטה המובנית אינה פעילה.

## מה שונה ב-SQLite לעומת Postgres

- **חיפוש מטושטש:** ב-Postgres הדמיון בין שמות מחושב ע"י `pg_trgm` באינדקס GIN. ב-SQLite אין מקבילה, אז
  אותו חישוב (trigram, אותה הגדרת דמיון והסף 0.3 לחיפוש) רץ בתוך התהליך מעל אינדקס בזיכרון שנבנה מטבלת המוצרים בכל עלייה
  (`src/normalize/trigramIndex.ts`). התוצאות דומות, אבל לא בהכרח זהות: סדר תוצאות בשוויון ציון יכול להיות שונה.
  זה מהיר לעשרות אלפי מוצרים; במאות אלפי מוצרים העלייה הראשונית תהיה איטית יותר וצריכת הזיכרון גבוהה יותר.
- **תהליך קליטה אחד למסד:** ב-SQLite השתמשו בקליטה המובנית ב-API, או כבו אותה והריצו scheduler נפרד. מניעת חפיפה היא בתוך התהליך, לא נעילה בין תהליכים. WAL מאפשר קריאה במקביל לכתיבה; אין להריץ כמה כותבים/עותקי API עם קליטה פעילה על אותו מסד.
  אינדקס החיפוש הוא לכל תהליך: מוצרים שנוצרו ע"י תהליך אחר יופיעו בחיפוש הבלתי-מדויק רק אחרי שה-API עולה מחדש (החיפוש לפי תת-מחרוזת והסל רואים אותם מיד).
- **טיפוסים:** מחירים נשמרים כ-REAL ומעוגלים ל-2 ספרות בפלט, תאריכים כ-ISO UTC.

## ממשק web

אפליקציית React + Vite + TypeScript בעברית (RTL, מובייל קודם) בתיקייה `web/`. בלי ספריות UI וגרפים: הגרף הוא SVG פשוט.

- **חיפוש מוצרים** (חיפוש המטושטש של ה-API) עם טווח מחירים ומספר רשתות
- **דף מוצר:** מחיר נוכחי לכל רשת וסניף, גרף היסטוריית מחיר לפי רשת (30/90 יום/הכל), אונליין בלבד
- **סל קניות:** הוספת מוצרים וכמויות, "איפה הכי זול" בין רשתות, חנויות אונליין בלבד, הצגת חנויות עם כיסוי חלקי. הסל נשמר בדפדפן
- **טריות נתונים:** מצב הקליטה האחרונה לכל רשת ורשימת התאמות לבדיקה ידנית

```bash
npm --prefix web install
npm run web              # מול ה-API המקומי (localhost:3000); /api מועבר ע"י Vite
npm run web:mock         # נתוני דמו בדפדפן, בלי API
npm --prefix web test    # בדיקות רכיבים (vitest + jsdom)
npm --prefix web run build
```

הגדרות (משתני סביבה של Vite, ראו `web/.env.example`):

| משתנה | משמעות |
|---|---|
| `VITE_API_BASE_URL` | כתובת בסיס ל-API. ברירת מחדל `/api` (proxy של Vite בפיתוח, nginx ב-docker). ל-API על origin אחר: כתובת מלאה, והפעילו בצד ה-API `CORS_ORIGIN` |
| `VITE_USE_MOCK=true` | נתוני דמו בדפדפן (גם `?mock=1` בכתובת) |
| `DEV_API_TARGET` | יעד ה-proxy של שרת הפיתוח, ברירת מחדל `http://localhost:3000` |

עם Docker: `docker compose up -d --build` מרים גם `api` (http://localhost:3000) וגם `web` (http://localhost:8080).
בנוסף ל-API נוסף `GET /stores?online=&text=&chain=&limit=` (רשימת סניפים), שהממשק משתמש בו לשמות סניפים.

## מבצעים ומועדונים (PromoFull)

הקליטה מושכת גם את קבצי **PromoFull** של חנויות האונליין (לצד PriceFull) ושומרת תמונת מבצעים עדכנית לכל חנות: תנאי המבצע (כמות מינימום, תוקף, מחיר מבצע או אחוז הנחה) ומועדון (`ClubID`: 0 = לכולם, אחרת מועדון של הרשת). קידודי המועדון שונים בין הרשתות והמפרסר מנרמל את כולם (`0 - כלל הלקוחות` של שופרסל, `(2=...|2=...)` של קרפור, `<Clubs><ClubId>` של רמי לוי).

- `GET /promos/clubs` - המועדונים שנמצאו בנתונים, לכל רשת, עם מספר המבצעים.
- `GET /products/<ref>/promos?clubs=<chain>:<clubId>,...` - לכל רשת: מחיר הבסיס, המחיר האפקטיבי בלי מועדון (`regular`) ועם המועדון שנבחר (`member`), ורשימת המבצעים עם התנאים המלאים.
- בדף המוצר בממשק: בחירת המועדונים שלך לכל רשת (נשמרת בדפדפן) והמחיר שתשלם בפועל לעומת המחיר הרגיל.

כללי היושרה של המחיר האפקטיבי (`src/promos/effective.ts`): מבצע מותנה (כמות מינימום, סכום סל, מוצר שקיל) **לא** מתגולל למחיר כותרת - מחיר הכותרת הוא תמיד מחיר ללא תנאי (מדף או מבצע פתוח), והמבצע המותנה מוצג בנפרד עם התנאי. מתנות וקופונים לא משפיעים על המחיר.

## קליטה יומית אוטומטית

ה-API כולל רענון יומי כברירת מחדל. להתקנות production יש גם שירות `scheduler` נפרד ב-`docker-compose.yml`; הפעילו רק מתזמן אחד למסד כפי שמוסבר למעלה.

```bash
docker compose up -d        # db + scheduler (+ mcp)
docker compose logs -f scheduler
```

**איך זה עובד**

1. השירות עולה, יוצר את הסכמה אם חסרה (`migrate`, בטוח להרצה חוזרת) וקובע ריצה יומית עם `node-cron`.
2. בכל ריצה, בזו אחר זו, **רמי לוי, קרפור, שופרסל, ויקטורי בלבד**: קבצי Stores לזיהוי חנויות אונליין (`StoreType=2`) ואז PriceFull האחרון לכל חנות אונליין. ללא זיהוי מאומת אין fallback לסניף פיזי.
3. קבצים שכבר נקלטו מדולגים, אז ריצה חוזרת באותו יום זולה ובטוחה.
4. בסוף: בדיקת טריות (`fresh` / `stale` / `never`) לכל רשת, מודפסת ללוג.

**כשל ברשת אחת לא עוצר את האחרות.** לכל רשת יש ניסיון חוזר עם backoff מעריכי (ברירת מחדל 3 ניסיונות: המתנה של 60 שניות, ואז 240).
רשת שנכשלה אחרי כל הניסיונות (למשל כשמקור או מראה לא זמינים) מסומנת `failed` והריצה ממשיכה. אם רק חלק מהקבצים נכשלו: `partial`, בלי ניסיון חוזר.
בסוף כל ריצה יש שורת סיכום, למשל `[daily-ingest] done: 3/4 chains ok, 1 failed`, ושורה לכל רשת עם מספר קבצים שנקלטו / דולגו / נכשלו.

**לשנות את השעה** - משתני סביבה (ב-`.env` ליד `docker-compose.yml`, או ב-shell):

| משתנה | ברירת מחדל | משמעות |
|---|---|---|
| `INGEST_HOUR` / `INGEST_MINUTE` | `6` / `0` | שעת הריצה היומית |
| `INGEST_TZ` | `Asia/Jerusalem` | אזור זמן |
| `INGEST_CRON` | (ריק) | ביטוי cron מלא, גובר על שעה/דקה. למשל `0 */6 * * *` = כל 6 שעות |
| `INGEST_RUN_ON_START` | `false` | `true` = ריצה אחת מיד כשהשירות עולה |
| `INGEST_RETRY_ATTEMPTS` / `INGEST_RETRY_BASE_SECONDS` | `3` / `60` | ניסיונות חוזרים והמתנה בסיסית |

אחרי שינוי: `docker compose up -d scheduler`. ברירת המחדל 06:00 נבחרה כדי שהרשתות כבר יפרסמו את קבצי הלילה.

**ריצה ידנית** (אותה לוגיקה בדיוק): `npm run ingest:all`, או בתוך docker: `docker compose run --rm scheduler node dist/src/scheduler/runOnce.js`.
לרשת אחת: `npm run ingest -- --chain shufersal`.

### אונליין מול סניפים פיזיים

המחירים באונליין שונים מהסניפים, ולכן **לא משווים ביניהם**. `POST /basket/cheapest` וכלי ה-MCP `cheapest_basket` משווים רק בתוך אותה קבוצה:

- ברירת מחדל: סניפים פיזיים בלבד.
- `area.online: true` (ב-MCP: `online: true`): חנויות אונליין בלבד.
- כל תוצאה כוללת `isOnline`.

אפשר לשנות את ברירת המחדל במקום אחד: `StoreArea.online` ב-`repository.ts`.

קבצי PromoFull נקלטים לצד PriceFull (מבצעים + מחירי מועדון, ראו "מבצעים ומועדונים"). מסלול ויקטורי עודכן ואומת ב-2026-10-08 (ראו להלן).

## דורש בדיקה חיה (לא אומת)

1. **פורטל publishedprices:** רק `RamiLevi` נבדק. שאר שמות המשתמש ב-`src/downloader/registry.ts` (יוחננוף, אושר עד, טיב טעם, חצי חינם, סטופ מרקט, פוליצר, קשת, דור אלון) נכתבו מזיכרון ויש לאמת אחד-אחד.
   סיסמה ריקה; ייתכנו רשתות עם סיסמה, captcha או חסימת קצב.
2. **שופרסל:** `catID=2` (PriceFull), `catID=5` (Stores) ופגינציה אומתו חי. חייבים להשמיט `storeId=0` בבקשה לכל הסניפים. קטגוריות 1/3/4 נשארו לפי התיעוד הציבורי; הבקשות אליהן הגיעו ל-timeout ולא אומתו כאן. קישורי blob פגים אחרי כ-30 דקות, לכן מורידים מיד אחרי הרישום. ריצה מלאה ארוכה עלולה לחייב רענון קישורים.
3. **ויקטורי:** ברירת המחדל היא מראה של קבצי המקור דרך `over.org.il`. `VictorySource(http, "direct")` שומר את ה-API הרשמי עבור סביבה עם גישה אליו. מזהה הרשת המאומת הוא `7290696200003`, לא `7290058103393`. המראה היא תלות חיצונית; כשל, ZIP חסר או נתונים ישנים אינם מוסתרים. בדיקות טריות רגילות עדיין חלות. מסלול רשמי ישיר עדיין לא אומת מהסביבה הזאת (חיבור TCP מצליח, TLS נתקע; חסימה לפי ארץ/ASN היא השערה עם תיעוד מצד שלישי, לא בדיקת A/B עצמאית).
4. **ChainId / SubChainId / StoreId:** בשופרסל נצפה `SubChainId=1` בקובץ Stores לעומת `001` בקובץ PriceFull. עדיין נשמרים הערכים המקוריים; צריך מדיניות איחוד מזהים לפני הסתמכות על חיבור הסניפים לחיפוש לפי אזור. כל רשת מדווחת אחרת (SubChainId `000`/`001`/ריק, StoreId עם אפסים מובילים, כמה ChainId לרשת אחת). המפתח לסניף כאן הוא `chain + subChain + store`. לבדוק שאין כפילות/פיצול סניפים.
5. **שמות תגיות וקידודים:** נצפה בקבצים חיים `ManufactureName` (ולא `ManufacturerName`), `PriceUpdateTime`, UTF-8 עם BOM במחירים, UTF-16LE בקובץ סניפים, קובץ סניפים לא דחוס בפורטל. הפרסר מכיר וריאציות (`Prices/Products/Product`, `ManufacturerName`, windows-1255) אבל לא נבדק מול כל רשת.
6. **שדה העיר:** גם קרפור ושופרסל מפרסמות קודים מספריים. ברמי לוי הוא קוד ישוב (`3000`). `area.text` עובד כרגע על טקסט (שם/כתובת/עיר), לכן צריך טבלת מיפוי קודי ישוב של הלמ"ס לשמות, אחרת חיפוש "ירושלים" לא ימצא סניפים שהעיר שלהם `3000`.
7. **ספי fuzzy** (0.8 / 0.55) ושמירת הגודל: ערכי פתיחה בלבד. לכוון מול דגימה אמיתית דרך `/quality/review`.
8. **pg_trgm:** נבדק עם Postgres 18 ועברית. ב-`postgres:16` של docker-compose צריך לוודא שההרחבה זמינה (היא חלק מ-contrib שבתמונה הרשמית) ולבדוק ביצועי אינדקס GIN על מיליוני מוצרים. `%` משתמש ב-`pg_trgm.similarity_threshold` של 0.3, כלומר אי אפשר להנמיך את `FUZZY_REVIEW_THRESHOLD` מתחת ל-0.3.
9. **ביצועים:** הקליטה כרגע שורה-שורה (כ-300 מוצרים בשנייה). לכמות מלאה כדאי batch insert / `COPY` ומקביליות בין סניפים.
10. **מבצעים מורכבים:** PromoFull נקלט ומוצג, אבל קומבינציות מבצעים (כפל מבצעים, AllowMultipleDiscounts), מבצעי סל (`MinPurchaseAmount`) וקופונים לא מחושבים לתוך מחיר אחד - הם מוצגים עם התנאים שלהם בלבד. קבצי Promo (דלתא) לא נקלטים, רק PromoFull.
11. **מחירי משקל ותוצרת טרייה:** קודים פנימיים שונים בין רשתות. ההתאמה לפי שם עלולה לחבר מוצרים שונים. לבדוק ידנית.
12. **תנאי שימוש וקצב:** לבדוק את תנאי השימוש של הפורטלים ולהגביל קצב; ה-User-Agent נקבע ב-`USER_AGENT`.

## רישוי

הקוד כאן נכתב מאפס ואינו מבוסס על קוד של פרויקט אחר. פורמט הקבצים נלמד מקבצים ציבוריים של הרשתות ומהתקנות השקיפות.

רק חנות מתומחרת אחת בכל רשת. שופרסל אינה חסומה בבדיקה זו: רשימת HTML לקחה 19-27 שניות לפני תשובה. timeout הרשימה הוא 90 שניות, שני retries כברירת מחדל. רשימות מסוננות צורכות מיד את קישור ה-SAS המקורי ושומרות את תוכן הקובץ עד הקליטה, בלי לבנות מחדש או לשמור קישורים שפג תוקפם.

ויקטורי: GET ל-`https://www.over.org.il/api/v1/datasets/e500decb-7bd5-41e6-a19f-f5c3ddf7b2c5/versions/latest`, בחירת `resources` מסוג ZIP, הורדת `download_url` והוצאת קובצי המקור. רק מזהה הרשת הנכון וסוגי הקבצים המבוקשים מתקבלים; כתובת ה-ZIP מוגבלת למארח ולנתיב המאומתים. הבקשות משתמשות ב-`User-Agent: Mozilla/5.0` וב-`Referer: https://www.over.org.il/`. אין הרשמה או טוקן. מסלול האונליין משתמש בחנות 097 שזוהתה כ-StoreType=2 בקובץ המקור, ללא fallback פיזי. ZIP של היום כלל גם PromoFull, אך קליטת מבצעים עדיין לא ממומשת. בדיקת Postgres ו-Docker לא הורצה באיטרציה זו.

### תמונות מוצרים

בתוצאות החיפוש ובדף המוצר מוצגות תמונות לפי ברקוד מדויק, עם fallback נגיש כאשר אין תמונה או שהטעינה נכשלת. קודי רשת פנימיים לא נשלחים למקור חיצוני. התמונות אינן חלק מקבצי PriceFull/PromoFull ואינן משנות את המחירים.

המקור הפעיל הוא **Open Food Facts**, לא אתרי הרשתות. התמונה הקדמית בעברית מועדפת. כל תמונה כוללת קישור לדף המקור ולרישיון CC BY-SA 3.0. התמונות מוצגות כפי שהן, בלי עיבוד או הורדת קבצי תמונה לשרת. זהו מאגר קהילתי עם כיסוי חלקי: תמונות עשויות להיות חסרות, ישנות או שגויות; אין הסקה לפי שם מוצר ואין הבטחה לכיסוי מותגים פרטיים או מוצרים שאינם מזון.

- `GET /products/:gtin/image` מחזיר URL ומקור/רישיון או `url: null`. יש `retryAfter` כשהמקור עמוס/לא זמין.
- מטא-דאטה בלבד נשמר ב-`data/product-images.json` (אפשר לשנות עם `IMAGE_CACHE_PATH`): תמונות לשבוע, חוסרים ליום. לא נשמר במאגר המחירים, ללא שינוי בסכמות SQLite/Postgres.
- יש הגבלה ל-12 פניות בדקה בכל תהליך, מתחת למגבלת OFF של 15. טעינה רק לכרטיסים הנראים במסך, בתור משותף, ללא polling או סריקה מלאה של הקטלוג. לכן תמונות ראשונות בחיפוש חדש מופיעות בהדרגה. מחירים זמינים מיד.
- `IMAGE_USER_AGENT` מאפשר לזהות את האפליקציה עם פרטי קשר. ברירת המחדל מזהה את הפרויקט הציבורי. בפריסה ציבורית יש להגדיר פרטי קשר ולמלא את טופס השימוש של OFF, בהתאם לתיעוד שלהם. הטופס לא מולא כחלק מה-PR.
- כמה רפליקות באותו IP חייבות להשתמש בשירות תמונות יחיד/מגבלה משותפת; אין לכתוב במקביל לאותו קובץ cache. תור ומגבלה ברמת תהליך אינם מגבלה מבוזרת. לפריסה גדולה יש להשתמש בייצוא המורשה של OFF במקום API לכל מוצר.
- הדפדפן מבקש את התמונה מ-OFF, כך שהמקור רואה IP וברקוד של התמונה. `no-referrer` מונע שליחת כתובת הדף. לא נשלחים חשבון, סל או פרטי מועדון.

בדיקת המקורות (2026-10-08): רמי לוי וקרפור חסמו את הגישה ל-storefront; שופרסל החזיר תמונת תחזוקה. ויקטורי נגיש ומציג תמונות Self Point ב-CDN, אבל הנתיבים כוללים מזהי retailer/internal ותאריך בנוסף לברקוד, ואינם תבנית כללית לפי ברקוד בלבד. תנאי רמי לוי (2.1, 6) וויקטורי (א.3) דורשים אישור כתוב לשימוש מחדש בתוכן. לכן **לא** מופעלים hotlinks לרשתות ולא נעשה proxy כדי לעקוף חסימה. אפשר להוסיף ספק רשמי לאחר קבלת הרשאה ומיפוי אמין.
